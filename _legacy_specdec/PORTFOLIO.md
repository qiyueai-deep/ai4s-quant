# 大模型算法岗作品集使用说明

本项目定位:独立的投机解码项目,从语料、训练、蒸馏、KV cache 解码引擎、离线基准到运行时自适应控制器全链路自包含,所有数字可由仓库内代码在单机 CPU 上复现。另有 SpecForge 作为独立的工程系统项目,两者在简历上分开写,不合并、不互相依赖。

## 一句话卖点

别人写"我调了投机解码库",这个项目写"接受率恒等式在我自己训练的模型对上验证到机器精度,最优 draft 长度由动态规划预测且与实测一致,运行时自适应控制器在不做任何离线调参的情况下达到 oracle 的 98.8%"。

## 面试高频问答

**为什么接受率恰好是 1 - TV(p,q)?**
拒绝概率是 min(1, p/q), 在 x ~ q 下取期望得 `sum_x q(x) min(1, p(x)/q(x)) = sum_x min(p(x), q(x))`, 归一化下等于 `1 - 0.5 sum|p-q|`。这是恒等式不是近似, 实测 1536 个真实分布对解析误差 3.3e-16, 独立蒙特卡洛误差 3.7e-3。

**Pinsker 下界有什么用?**
`D(p||q) >= 2 TV^2` 给出 `alpha >= 1 - sqrt(D/2)`, 把蒸馏的 KL 指标和在线接受率连起来, 可反解"要目标加速, KL 需压到多少"。本项目中蒸馏把 KL 从 0.387 压到 0.109, 保证的下界从 0.560 升到 0.766。

**为什么 K 越大不一定越快, 最优值为什么有限?**
一轮产出 E[N_K] 受 `1/(1-alpha)` 上界约束, 成本 c0 + gK 线性增长, 所以 S(K) 趋于 0, 最大值必在有限 K。实测 K = 4 峰值 1.279x, K = 16 掉到 0.759x, K = 32 只有 0.510x。本模型还有一个额外效应: 接受率随上下文深度衰减 (轮内首 slot 0.89, 越深越低), 常数 alpha 的几何模型会系统性失准, 这是我改用逐位置一致率动态规划的原因。

**你的 K* = 4 是推导出来的还是拟合出来的?**
诚实答: 有限最优的存在性是推导的, K* 的数值依赖两个实测校准的成本系数 (c0 = 1.6977, g = 0.2233, R^2 = 0.988)。接受率部分不靠拟合: 解码是确定性的, 我在每条 prompt 的贪婪路径上直接测每个位置的一致率, 用后向递归精确算期望验证轮数, E[N] 模型与实测最大误差 0.075, 预测 K* 与实测差 0, 排序相关 0.988。

**自适应控制器比固定 K 强在哪? 它需要什么信息?**
固定 K 对所有上下文用同一个长度, 而接受率依赖上下文 (draft 低熵桶 0.794, 高熵桶 0.569), 全局最优 K 在平坦峰值附近, 选错一侧就跌破 1.0。控制器只需要两个可直接测量的量: 验证前向与 draft 步的耗时, 加上运行中的接受率流。它不做离线扫参就达到 oracle 的 98.8% (1.265x vs 1.279x)。

**接受率估计怎么做的, 有没有坑?**
有, 而且踩过。第一版用 accepted/proposed 更新 EWMA, 但一轮里从未被测到的 slot 不是 Bernoulli 失败, 混进分母会把估计拉到 0.53 (真实 0.70), 控制器因此选 K 过小。改成只统计实际测过的 slot: 每轮 match 个成功, mismatch 结束再记一个失败, 并加 Laplace 平滑。第二个坑: 熵分桶的阈值最初按 target 的熵校准, 而运行时喂的是 draft 的熵, 两者量级完全不同, 导致所有上下文被路由进同一个桶, 修正为联合 rollout 下按 draft 熵的中位数校准。

**投机解码的正确性怎么保证?**
验证步骤是精确的: 提案只在等于 target 贪婪 token 时被接受, bonus 取的是 target 在首个拒绝位的 argmax, 因此输出逐 token 等于纯贪婪解码。单测对 K 从 1 到 32 以及两个控制器逐一断言输出相等, 基准里每个配置也核对全部 24 条 prompt。实现上有一个正确性攸关的细节: bonus 的 KV 不能提前算, 它作为下一轮验证输入的首位在正确位置上被计算, 否则位置编码错位。

**蒸馏为什么没有全面碾压同预算 SFT?**
实测 KL 蒸馏占优 (0.109 vs 0.387), 但贪婪一致率只从 0.844 升到 0.865。分布匹配与 argmax 对齐是不同目标, 贪婪投机解码只消耗后者, 蒸馏损失里 0.3 的硬 CE 权重就是两者的旋钮。这个权衡是测出来的, 我不会宣称蒸馏在所有指标上更好。

**墙钟数字的可信度?**
共享 CPU 墙钟漂移大, 同一代码不同批次的最优 K 加速在 1.12 到 1.28 之间波动过。最终方案是配对重复: 每轮基线与全部配置背靠背运行, speedup 逐对计算取 5 次中位数, 慢相位在分子分母同时出现而抵消。每个配置的最小最大区间都留在 benchmark.json 里, 报告时一并给出。
